# 통합 피드백 게시판 기획·개발 계획

## 1. 목적과 화면 구분

5개 시스템이 서로 다른 경로로 받던 피드백을 한곳에 모아 전체 현황과 처리 결과를 확인한다.

- 홈: 5개 시스템 전체 현황을 보여 주는 조회 전용 대시보드
- 프로젝트 상세: 선택한 프로젝트의 피드백을 처리하는 작업 화면

## 2. 역할과 권한

| 역할 | 코드 | 권한 |
|---|---|---|
| 개발자 | `DEVELOPER` | 전체 조회·수정, 상태 변경, 답변, 유형·중요도 변경, 계정 승인과 역할 부여 |
| 열람자 | `VIEWER` | 전체 조회, 대시보드 조회, 우선 처리 요청 |
| 일반 사용자 | `USER` | 피드백 등록, 내 문의와 답변 조회 |

모든 개발자는 같은 권한을 가진다. 열람자는 상태 변경과 답변을 할 수 없다.

## 3. 공통 도메인 규칙

### 처리 상태

| 상태 | 코드 | 전환 시점 | 칸반 위치 |
|---|---|---|---|
| 접수 | `RECEIVED` | 등록 직후 | 1열 진행 전 |
| 처리 중 | `IN_PROGRESS` | 수정 작업 착수 | 2열 진행 중 |
| 처리 완료 | `DONE` | 추가 조치가 필요 없음 | 3열 완료 |
| 반영 불가 | `REJECTED` | 중복·오신고 또는 반영이 어려움 | 보드 밖 별도 목록 |

### 유형과 중요도

- 유형은 `FEATURE_REQUEST`, `BUG_REPORT`, `OTHER` 세 가지다.
- 중요도는 `LOW`, `MEDIUM`, `HIGH` 세 단계다.
- `reported_priority`는 작성자가 느끼는 긴급도이며 정렬에 사용하지 않는다.
- `priority`는 개발자가 판단한 정렬 기준값이다.

### 우선 처리 요청

열람자가 먼저 처리해 달라고 요청하는 토글 기능이며 건수 제한은 없다. 요청되면 `priority`를 `HIGH`로 올리고 개발자 전원에게 메일을 보낸다. 우선 처리 요청이 켜진 항목은 어떤 정렬에서도 목록 최상단에 고정한다.

## 4. 화면 규칙

- 대상 시스템에서 진입한 사용자 화면은 `?site=aipms` 같은 쿼리로 프로젝트를 고정하며 작성자가 바꿀 수 없다.
- 사용자 홈의 “새 질문 적기”에서 시작한 경우에만 프로젝트 드롭다운을 노출한다.
- 관리 화면은 하단 원형 디스크로 프로젝트를 바꾸고 상단 탭으로 개발 보드와 답변 메뉴를 바꾼다.

## 5. 개발 전제

1. 엔티티, 상수, API 명세와 스텁, 보안 경로, 데모 로그인, 시드, 라우트와 공통 의존성은 0-1단계에서 함께 확정한다.
2. 실제 인증은 7단계에서 붙이며 그전에는 서버가 제공하는 데모 계정을 사용한다. 화면은 역할을 추측하지 않고 서버 응답의 `role`만 사용한다.
3. 같은 단계에서 한 담당자에게 큰 작업을 두 개 이상 배정하지 않는다.

### 데모 계정

| 계정 | 역할 | 확인 대상 |
|---|---|---|
| `dev@demo.local` | `DEVELOPER` | 관리 화면 전체와 변경·답변·승인 |
| `viewer@demo.local` | `VIEWER` | 조회, 우선 처리 요청, 수정 API의 403 |
| `user@demo.local` | `USER` | 사용자 홈, 내 문의, 답변 수신 |
| 로그아웃 | 없음 | 비회원 등록 경로 |

`POST /api/dev/login`은 `dev` 프로필에서만 등록하고 운영 프로필에서는 404를 반환한다.

## 6. 협업 경계

- `SecurityConfig`: 관리용 API·인프라 담당 소유. 0-1단계에서 전체 경로를 선언한다.
- `Feedback`, `FeedbackRepository`: 사용자용 API 담당 소유. 관리용 담당은 조회 메서드 추가 전에 공유한다.
- 프론트 라우터: 0-1단계에서 모든 경로를 등록하며 이후 새 경로를 임의로 추가하지 않는다.
- `components/common`: 사용자 화면·디자인 담당 소유. 필요한 요소가 없으면 각 화면에 임시 구현한 뒤 통합 단계에서 흡수한다.
- `package.json`, `build.gradle`: 공통 기반에서 의존성을 확정한다.
- `application.properties`: 관리용 API·인프라 담당 소유.
- 관리용 응답은 `AdminFeedbackResponse`, 사용자 내 문의 응답은 `MyFeedbackResponse`로 분리한다.

프론트는 0-1단계 스텁 응답을 사용해 백엔드 구현을 기다리지 않고 개발한다.

## 7. 단계별 계획

### 0-1단계 · 공통 기반

| 산출물 | 완료 조건 |
|---|---|
| 엔티티 4종과 스키마 | H2에서 `projects`, `app_users`, `feedbacks`, `answers`와 제약 조건 확인 |
| 공통 상수 | 유형·상태·중요도·역할 값이 백엔드와 프론트에서 동일 |
| API 명세와 스텁 | 제품 엔드포인트 12개가 Swagger에 노출되고 목 데이터로 200 반환 |
| 보안 경로 | `/api/feedbacks/**` 공개, `/api/admin/**` 인증 및 역할별 수정 제한 |
| 데모 로그인 | `dev` 프로필에서 세 계정과 로그아웃 전환, 다른 프로필에서 404 |
| 시드 | 프로젝트 5건과 피드백 40건을 상태·유형·중요도별로 분산 |
| 라우트 | 사용자·관리 화면 전체 경로가 빈 화면으로 열림 |
| 라이브러리 | 라우팅, 드래그, 차트, 아이콘 의존성 설치 |
| 로컬 실행 | 백엔드와 프론트 동시 기동 및 Vite의 `/api` 프록시 호출 성공 |

### 0-2단계 · 디자인 기반

- 색상·타이포그래피를 한곳에 정의한다.
- 상태 배지 4종과 중요도 칩 3종을 공용 컴포넌트로 만든다.
- 사용자 화면 4종과 관리 화면 2종의 배치를 확정한다.

### 1단계 · 기본 기능

- 사용자용: 비회원·회원 피드백 등록 API와 공통 검증 오류
- 관리용: 목록 API, 필터·정렬, 권한 검사
- 관리 화면: 레이아웃, 상단 탭, 3열 칸반과 반영 불가 영역
- 사용자 화면: 로그인 화면과 비회원 경고 팝업

### 2~8단계 요약

1. 2단계: 관리 화면을 실제 API와 연결하고 공용 컴포넌트를 통합한다.
2. 3단계: 답변·내 문의·상태 변경·대시보드와 사용자 홈·작성 화면을 구현한다.
3. 4단계: 사용자 등록 흐름과 관리자 상태 변경 흐름을 통합한다.
4. 5단계: 우선 처리 요청, 집계 성능, 프로젝트 디스크, 차트와 오류·빈 상태를 마감한다.
5. 6단계: 이메일 알림, 답변 흐름과 계정 관리를 완성한다.
6. 7단계: 데모 로그인을 Google OAuth로 교체하고 역할별 전체 흐름을 재검증한다.
7. 8단계: PostgreSQL 운영 배포, 5개 시스템 진입 링크와 전 구간을 최종 점검한다.
