# 통합 피드백 게시판 기획안

부산대학교 AI융합교육원이 운영하는 5개 시스템의 피드백을 한 곳에서 수집하고 처리하는 서비스의 설계 문서다.

- 문서 버전: v1.1
- 최종 수정: 2026-09-15
- 관련 문서: [README](../README.md), [개발환경 설정 가이드](setup-guide.md)

---

## 1. 개요

### 1-1. 목적

현재 5개 시스템은 각각 별도의 경로로 피드백을 받고 있어 전체 접수 현황과 처리 결과를 확인할 수 없다.
이 서비스는 수집 창구를 하나로 모으고, 이용 목적이 다른 세 집단에 각각 필요한 화면을 제공한다.

| 이용자 | 현재 문제 | 제공하는 기능 |
|---|---|---|
| 실사용자 | 신고 창구가 시스템마다 다르고 처리 여부를 알 수 없다 | 시스템별 링크를 통한 피드백 등록, 답변과 진행 상태 조회 |
| 개발자 | 피드백이 여러 경로로 분산되어 누락된다 | 프로젝트별 칸반 보드와 답변 대기열 |
| 교육원 운영진 | 5개 프로젝트의 전체 현황을 한 번에 볼 수 없다 | 전체 현황 대시보드 |

개발자는 프로젝트 단위로 나누어 보아야 하고, 운영진은 전체를 합쳐 보아야 한다.
두 요구를 한 화면에서 만족시킬 수 없으므로 **화면을 목적별로 분리한다.**
홈은 전체 현황 대시보드, 프로젝트 상세는 해당 프로젝트의 작업 화면으로 둔다.

### 1-2. 대상 사이트

| 코드 | 이름 |
|---|---|
| `codeplace` | 코드플레이스 |
| `aipms` | AIPMS |
| `aicms` | AICMS |
| `aicap` | AI역량지원시스템 |
| `srvadm` | pickle (서버관리) |

프로젝트 목록은 DB에서 관리하며 추가할 수 있다. 각 프로젝트는 화면 이동 메뉴에 사용할 로고 이미지를 가진다.

## 2. 시스템 구성

React 애플리케이션 하나를 경로로 분리하고, 스프링부트 서버 하나를 공유한다.

```
   실사용자  ──▶  /  ·  /write  ·  /my      사용자용 화면
                                              │
   개발자    ──▶  /admin/**                   │  /api/**
   열람자    ──▶  (인증 + 권한 검사)          │
                                              ▼
                              Spring Boot 3.5.6 / JDK 21 / JPA
                                              │
                                        PostgreSQL
```

- 프론트엔드: React (Vite) 단일 프로젝트. 라우팅으로 사용자용과 관리용을 구분한다.
- 백엔드: Spring Boot 3.5.6 / JDK 21 / JPA / Spring Security. 로컬 개발은 H2, 운영은 PostgreSQL을 사용한다.
- 권한 검사는 화면이 아니라 API에서 수행한다. 관리용 주소를 직접 입력해도 데이터를 얻을 수 없다.

## 3. 사용자와 권한

### 3-1. 역할

역할은 네 가지이며, 관리용 사이트에 접근할 수 있는 역할은 `DEVELOPER`와 `VIEWER` 두 가지다.

| 역할 | 코드 | 권한 |
|---|---|---|
| 개발자 | `DEVELOPER` | 전체 프로젝트 조회 및 수정, 상태 변경, 답변 작성, 유형·중요도 변경, 계정 승인과 역할 부여 |
| 열람자 | `VIEWER` | 전체 프로젝트 조회, 대시보드 조회, 우선 처리 요청 |
| 일반 사용자 | `USER` | 피드백 등록, 자신이 등록한 피드백과 답변 조회 |
| 비회원 | 없음 | 피드백 등록 |

- 모든 개발자는 동일한 권한을 가진다. 담당 프로젝트를 구분하지 않으므로 부재 시 다른 개발자가 대신 처리할 수 있다.
- 계정 승인 권한 또한 모든 개발자가 가진다. 승인 절차를 한 사람에게 의존하지 않기 위한 결정이다.
- 열람자는 상태 변경과 답변 작성을 할 수 없다. 처리 진행 상황이 의도치 않게 바뀌는 것을 방지한다.

### 3-2. 계정 승인

관리용 사이트는 승인된 계정만 사용할 수 있다.

| 순서 | 처리 내용 | 계정 상태 |
|---|---|---|
| 1 | 구글 로그인으로 `/admin`에 최초 접근하면 계정 레코드를 생성한다 | `PENDING` |
| 2 | 승인 대기 안내 화면을 표시하고 모든 기능을 차단한다 | `PENDING` |
| 3 | 기존 개발자가 역할을 지정하고 승인한다 | `ACTIVE` |
| 4 | 부여된 역할의 권한으로 이용한다 | `ACTIVE` |

최초 개발자 계정 한 건은 DB에 직접 등록해 초기화한다. 이후의 계정은 화면에서 승인한다.

## 4. 피드백 규칙

### 4-1. 유형

| 유형 | 코드 | 정의 |
|---|---|---|
| 오류 신고 | `BUG` | 서비스 이용 중 발생한 오류 또는 비정상 동작 |
| 기능 제안 | `FEATURE` | 추가를 요청하는 기능 |
| 기타 의견 | `ETC` | 위 두 유형에 해당하지 않는 의견 |

유형은 작성자가 선택하고, 개발자가 변경할 수 있다.
작성자가 유형을 잘못 선택한 경우 분류를 바로잡기 위한 기능이다.

### 4-2. 진행 상태

상태는 네 가지이며, 칸반 보드는 이 중 세 가지를 열로 사용한다.

| 상태 | 코드 | 전환 시점 | 전환 주체 | 칸반 위치 |
|---|---|---|---|---|
| 접수 | `RECEIVED` | 피드백이 등록된 직후 부여되는 초기 상태 | 시스템 | 1열 (진행 전) |
| 처리 중 | `IN_PROGRESS` | 내용을 확인하고 수정 작업에 착수한 시점 | 개발자 | 2열 (진행 중) |
| 처리 완료 | `DONE` | 수정이 반영되어 추가 조치가 필요 없는 시점 | 개발자 | 3열 (완료) |
| 반영 불가 | `REJECTED` | 중복·오신고이거나 현재 반영이 어렵다고 판단한 시점 | 개발자 | 보드 밖 (별도 목록) |

`REJECTED`는 칸반 열을 차지하지 않는다. 보드 하단의 "반영 불가 N건" 영역에서 펼쳐 조회한다.
보드에는 처리해야 할 항목만 남기기 위한 구성이다.

상태 배지 색상은 접수 파랑, 처리 중 주황, 처리 완료 초록, 반영 불가 회색을 사용한다.

### 4-3. 중요도

중요도 값은 `HIGH`, `NORMAL`, `LOW` 세 가지이며 기본값은 `NORMAL`이다.
서로 다른 두 필드로 관리한다.

| 필드 | 입력 주체 | 용도 |
|---|---|---|
| `reported_priority` | 작성자가 등록 시 선택 | 작성자가 체감한 긴급도. 참고용이며 정렬에 사용하지 않는다 |
| `priority` | 개발자가 확정 | 정렬 기준값. 등록 시점에는 `reported_priority`와 같은 값으로 시작한다 |

작성자가 선택한 값을 그대로 정렬에 사용하면 대부분의 피드백이 `HIGH`로 등록되어 정렬이 무의미해진다.
따라서 작성자의 입력은 보존하되, 정렬은 개발자가 확정한 값으로만 수행한다.
상세 화면에는 두 값을 함께 표시한다.

### 4-4. 우선 처리 요청

열람자가 특정 피드백을 먼저 처리하도록 요청하는 기능이다.

| 항목 | 동작 |
|---|---|
| 버튼 동작 | 토글. 다시 누르면 해제된다. 요청 가능 건수에 제한은 없다 |
| 중요도 | 요청 시 `priority`를 `HIGH`로 변경한다 |
| 알림 | 요청 시 개발자 전원에게 메일을 발송한다 |
| 정렬 | 어떤 정렬 기준을 선택해도 목록 최상단에 고정하고 배지를 표시한다 |
| 해제 | 요청한 열람자 본인만 해제할 수 있다 |

요청 이후 개발자가 `priority`를 다시 낮추는 것은 가능하다. 이 경우에도 배지와 상단 고정은 유지된다.

### 4-5. 정렬과 필터

정렬은 우선 처리 요청 여부를 1순위로 적용한 뒤, 선택한 기준을 2순위로 적용한다.

| 정렬 기준 | 순서 |
|---|---|
| 중요도순 | 우선 처리 요청 → `HIGH` → `NORMAL` → `LOW` → 동일 시 최신순 |
| 최신순 | 우선 처리 요청 → 등록일 내림차순 |
| 오래된순 | 우선 처리 요청 → 등록일 오름차순 |

필터 항목은 사이트, 진행 상태, 유형, 기간, 회원 여부다.

## 5. 사용자용 사이트

### 5-1. 화면 흐름

```
                        로그인 화면
                    ┌────────┴────────┐
              구글 로그인          비회원으로 계속
                    │                  │
                    │            비회원 경고 팝업
                    │            ┌─────┴─────┐
                    │        [로그인]      [계속]
                    │            │            │
                    ▼            │            │
              홈 (내 문의) ◀──────┘            │
                    │                         │
             새 질문 적기                      │
                    │                         │
                    └──────────┬──────────────┘
                               ▼
                        피드백 작성 화면
                               ▼
                    "질문이 접수되었습니다"
```

비회원은 홈을 거치지 않고 작성 화면으로 이동한다.

### 5-2. 사이트 지정

피드백의 대상 사이트는 진입 링크로 결정한다.

- 각 시스템에 `https://{서비스주소}/?site=aipms` 형식의 링크를 배치한다.
- 링크로 진입한 경우 사이트가 자동 지정되며 작성자는 변경할 수 없다. 대상 사이트 오분류를 방지한다.
- 회원이 홈에서 `새 질문 적기`를 선택한 경우에는 사이트 정보가 없으므로, 이 경우에만 사이트 선택 드롭다운을 표시한다.

### 5-3. 화면 명세

#### 로그인 화면 `/`

서비스 설명과 함께 `구글로 로그인`, `비회원으로 계속` 두 개의 버튼을 배치한다.

`비회원으로 계속`을 선택하면 다음 내용의 모달을 표시한다.

- 안내 문구: 비회원은 답변을 받을 수 없으며, 등록한 내용과 진행 상태를 다시 확인할 수 없다.
- `로그인` 버튼: 구글 로그인으로 이동한다.
- `계속` 버튼: 작성 화면으로 이동한다.

#### 홈 `/home` — 회원 전용

- `새 질문 적기` 버튼
- 본인이 등록한 피드백 목록. 최신순으로 정렬하며 사이트, 제목, 유형, 상태 배지, 등록일, 답변 여부를 표시한다.
- 목록이 비어 있는 경우 안내 문구를 표시한다.

#### 피드백 작성 `/write`

| 항목 | 입력 형태 | 필수 | 제약 |
|---|---|---|---|
| 사이트 | 고정 표시 또는 드롭다운 | 필수 | 링크로 진입한 경우 변경 불가 |
| 유형 | 라디오 버튼 3개 | 필수 | 기본 선택값 없음 |
| 긴급도 | 라디오 버튼 3개 | 필수 | 기본값 `NORMAL` |
| 제목 | 단일 행 입력 | 필수 | 최대 100자 |
| 내용 | 여러 행 입력 | 필수 | 10자 이상 2,000자 이하 |

등록에 성공하면 "질문이 접수되었습니다" 팝업을 표시한다.
회원은 홈으로, 비회원은 로그인 화면으로 이동하며 비회원 세션은 종료된다.

#### 문의 상세 `/my/{id}` — 회원 전용

등록한 제목과 내용, 유형, 등록일, 현재 상태 배지, 개발자 답변을 표시한다.
답변이 없는 경우 안내 문구를 표시한다.

작성자는 등록한 피드백을 수정하거나 삭제할 수 없다.
처리 중인 항목이 변경되거나 삭제되면 처리 이력이 어긋나기 때문이다.

## 6. 관리용 사이트

### 6-1. 화면 구조

화면 이동은 두 축으로 구성한다. 하단은 프로젝트를 전환하고, 상단은 선택된 프로젝트 내부의 메뉴를 전환한다.

```
┌─────────────────────────────────────────────────────┐
│  통합 피드백 게시판                    계정 이름 ▾   │  공통 헤더
├─────────────────────────────────────────────────────┤
│ ╭──────────╮ ╭────────╮                             │  상단 탭
│ │ 개발 보드 │ │  답변  │                             │  (프로젝트 내 메뉴)
├─┴──────────┴─┴────────┴─────────────────────────────┤
│                                                     │
│              칸반 보드 또는 답변 목록                 │
│                                                     │
├─────────────────────────────────────────────────────┤
│                   ⬤ 선택된 프로젝트                  │  하단 디스크
│              ○                      ○               │  (프로젝트 전환)
│         ╲______화면 아래로 잘림______╱               │
└─────────────────────────────────────────────────────┘
```

- **하단 디스크**: 원형 메뉴의 위쪽 일부만 화면에 노출한다. 프로젝트 로고를 호를 따라 배치하고, 좌우 드래그 또는 로고 클릭으로 회전한다. 최상단에 위치한 프로젝트가 선택된다. 슬롯 하나는 홈(전체 현황 대시보드) 진입점으로 사용한다.
- **상단 탭**: 브라우저 탭 형태로 `개발 보드`와 `답변` 두 개를 배치한다.

### 6-2. 홈 — 전체 현황 대시보드

조회 전용 화면이다. 이 화면에서는 상태 변경이나 답변 작성을 수행하지 않는다.
상단에 상태별 건수 카드를 배치하고, 그 아래에 차트 네 개, 하단에 우선 처리 요청 목록과 최근 접수 10건을 배치한다.

| 지표 | 산출 방식 |
|---|---|
| 상태별 건수 | 상태별 건수 합계 |
| 프로젝트별 현황 | 프로젝트와 상태의 교차 집계. 누적 막대 |
| 유형별 비율 | 유형별 건수를 전체 건수로 나눈 값. 도넛 |
| 기간별 추이 | 일자별 접수 건수. 기본 조회 범위 30일. 선 그래프 |
| 평균 처리 소요 시간 | `closed_at - created_at`의 평균. `DONE`과 `REJECTED`만 집계 |
| 이용자 수 | 피드백을 1건 이상 등록한 고유 사용자 수. 비회원은 별도 집계 |

### 6-3. 개발 보드 탭

진행 전, 진행 중, 완료 세 개 열로 구성한 칸반 보드다.

- 카드 표시 항목: 우선 처리 요청 배지, 중요도, 제목, 유형, 경과일, 회원 여부, 답변 여부
- 카드를 다른 열로 이동하면 상태가 변경된다. 카드 선택 시 열리는 상세 패널에서도 변경할 수 있다.
- 상세 패널에서 전체 내용 확인, 유형 변경, 중요도 변경, 답변 화면 이동을 제공한다.
- 상단에 정렬, 유형, 기간 필터를 배치한다. 정렬은 각 열 내부에 적용한다.
- 보드 하단에 반영 불가 항목을 접은 상태로 배치한다.

### 6-4. 답변 탭

답변을 작성하는 목록형 화면이다. 기본 필터는 `답변 필요`, 기본 정렬은 오래된순이다.

- 항목 표시: 우선 처리 요청 배지, 중요도, 제목, 유형, 등록일, 작성자 회원 여부, 현재 상태, 내용 일부
- 비회원이 등록한 피드백은 답변 대상이 아니다. 비회원 표시와 함께 비활성 상태로 노출하며 답변 버튼을 제공하지 않는다.
- 답변은 피드백 1건당 1건만 등록할 수 있으며, 등록 후 수정할 수 있다.
- 답변 등록 시 상태를 `DONE`으로 함께 변경하는 선택 항목을 제공한다.

### 6-5. 계정 관리 — 개발자 전용

헤더의 계정 메뉴에서 진입한다.
승인 대기 목록에서 이메일, 이름, 가입일을 확인하고 역할을 지정해 승인하거나 거절한다.
기존 계정의 역할 변경과 비활성화도 이 화면에서 처리한다.

## 13. 개발 순서

### 13-1. 전제

**공통 세팅은 AI로 먼저 만든다.** 0단계의 엔티티, 공통 상수, API 명세와 스텁 응답, 보안 경로 패턴,
데모 로그인, 시드 데이터, 라우트 선언은 사람이 나누어 만들지 않고 AI로 생성한다. 이 부분을 나누어 만들면 엔티티와 명세가 서로 어긋나 이후 단계가 전부 막힌다.
생성 결과는 **전원이 읽고 이해한 뒤** 1단계를 시작한다. 이해하지 못한 코드 위에서는 이후 작업을 진행할 수 없다.

**인증은 마지막에 붙인다.** 구글 OAuth 연동은 7단계에서 수행하고, 그 전까지는 데모 계정으로 개발한다.
외부 서비스 발급 절차가 개발 전체를 막지 않도록 하고, 역할별 화면을 계정 전환만으로 즉시 확인하기 위한 결정이다.

**한 사람에게 같은 단계에서 큰 작업을 두 개 이상 배정하지 않는다.** 각 단계는 1~2주 안에 끝나는 분량으로 나눈다.
분량이 넘치면 단계를 쪼개고, 작업을 합치지 않는다.

### 13-2. 데모 계정

`dev` 프로필에서만 동작하는 로그인 API로 역할을 전환한다.

| 계정 | 역할 | 확인 대상 |
|---|---|---|
| `dev@demo.local` | `DEVELOPER` | 관리용 화면 전체, 상태 변경, 답변, 계정 승인 |
| `viewer@demo.local` | `VIEWER` | 조회 권한, 우선 처리 요청, 수정 API 403 확인 |
| `user@demo.local` | `USER` | 사용자용 홈, 내 문의, 답변 수신 |
| 로그인하지 않음 | 없음 | 비회원 등록 경로 |

- `POST /api/dev/login`은 계정 식별자를 받아 실제 로그인과 동일한 세션을 발급한다.
  이 엔드포인트는 `dev` 프로필에서만 빈으로 등록하고 운영 프로필에서는 등록하지 않는다.
- 프론트엔드는 개발 모드에서만 노출되는 계정 전환 위젯에서 이 API를 호출한다.
- **화면은 역할을 자체 판단하지 않는다.** 서버가 내려준 역할 값만 사용한다.
  이 규칙을 지키면 7단계에서 인증 방식을 교체해도 화면 코드를 수정할 필요가 없다.
- 7단계의 교체 대상은 로그인 엔드포인트와 사용자 조회 부분으로 한정된다.

### 13-3. 담당 구분

4명이 나누어 진행한다. 담당 기호는 아래와 같이 사용하며 실제 배정은 착수 회의에서 정한다.

| 기호 | 담당 영역 | 주요 산출물 |
|---|---|---|
| A | 백엔드 · 도메인과 사용자용 API | 피드백 등록·조회, 답변, 내 문의, 우선 처리 요청 |
| B | 백엔드 · 관리용 API와 인프라 | 목록 조회(필터·정렬), 권한 검사, 대시보드 집계, 알림, 인증 |
| C | 프론트엔드 · 관리용 화면 | 칸반 보드, 답변 탭, 하단 디스크, 대시보드 |
| D | 디자인 · 사용자용 화면 | 스타일 규칙과 공용 컴포넌트, 화면 시안, 사용자용 화면 4종 |

- D는 디자인 작업 비중이 높은 담당이다. **구현 분량은 네 명 중 가장 적게 배정한다.**
  사용자용 화면은 화면 수가 적고 상호작용이 단순해 디자인 작업과 병행하기에 적합하다.
- 상호작용이 복잡한 화면(칸반 드래그, 디스크 회전, 차트)은 C가 맡는다.
- **D의 스타일 규칙과 공용 컴포넌트는 0단계에서 먼저 나온다.** C가 그 위에서 관리용 화면을 시작한다.
  두 사람이 각자 스타일을 만들면 같은 서비스로 보이지 않고, 나중에 한쪽을 다시 만들어야 한다.

통합 단계에서는 사용자용을 A와 D가, 관리용을 B와 C가 연결한다.
담당별로 대화 상대가 정해져 있어 통합 시 네 명이 한꺼번에 얽히지 않는다.

### 13-4. 공유 파일과 충돌 방지

동시에 작업하면 같은 파일을 고치는 지점과 다른 담당을 기다리는 지점이 생긴다.
아래 규칙으로 두 경우를 모두 0단계에서 없앤다.

#### 폴더 분리

백엔드는 `feedback`, `admin`, `auth`, `notification`으로, 프론트엔드는 `pages/user`, `pages/admin`, `components/common`으로 나눈다.
각자 자기 폴더 안에서만 파일을 만든다.

#### 공유 파일의 소유자

| 파일 | 소유 | 다른 담당이 수정해야 할 때 |
|---|---|---|
| `SecurityConfig` | B | 0단계에서 경로 패턴을 모두 선언하므로 이후 열지 않는다 |
| `Feedback` 엔티티, `FeedbackRepository` | A | B는 조회 메서드만 추가하고 커밋 전에 공유한다 |
| 프론트엔드 라우터 정의 | 0단계 산출물 | 모든 경로를 빈 화면으로 미리 등록하므로 추가하지 않는다 |
| `components/common` | D | 요청한다. 대기가 길어지면 자기 화면 안에 임시로 만들고 통합 단계에서 D가 흡수한다 |
| `package.json`, `build.gradle` | 0단계 산출물 | 라이브러리는 0단계에 일괄 설치한다. 추가가 필요하면 팀에 먼저 공유한다 |
| `application.properties` | B | B에게 요청한다 |

#### 응답 DTO는 용도별로 나눈다

관리용 목록과 사용자용 조회는 같은 피드백을 서로 다른 범위로 내보낸다.
공용 DTO 하나를 두면 A와 B가 같은 클래스에 필드를 붙였다 빼는 일이 반복되고, 사용자에게 내부 필드가 노출될 위험이 생긴다.

| DTO | 사용처 | 포함 범위 |
|---|---|---|
| `AdminFeedbackResponse` | 관리용 목록과 상세 | 작성자 정보, 중요도 2필드, 우선 처리 요청 여부, 내부 타임스탬프 |
| `MyFeedbackResponse` | 사용자용 내 문의 | 제목, 내용, 유형, 상태, 등록일, 답변 |

#### 기다리지 않는다

- C와 D는 0단계의 스텁 응답으로 화면을 끝까지 만든다. 백엔드 완성을 기다리지 않는다.
- 공용 컴포넌트에 없는 요소가 필요하면 자기 화면 안에 임시로 만든다. D의 작업을 기다리지 않는다.
- 매일 `develop`의 최신 내용을 각자 브랜치에 반영한다.
- 브랜치는 작업 단위로 자른다. 이름은 `feature/{영역}-{작업}` 형식을 사용한다.

### 13-5. 단계별 진행

```
0단계  AI 생성 ████ → 전원 확인 ██ / D 디자인 기반 ███    분담 전
1단계  A ███  B ███  C ███  D ██          동시
2단계  통합 ██                            합류
3단계  A ███  B ███  C ███  D ███         동시
4단계  통합 ██                            합류
5단계  A ██   B ██   C ███   D ██         동시
6단계  B ███  C ██   D ██                 일부
7단계  B ███  + 전원 확인                  인증 전환
8단계  전원 ██                            배포
```

#### 0-1단계 · 공통 기반 (AI 생성, 전원 확인)

사람에게 배정하지 않는다. AI로 생성하고 전원이 확인한다.

| 산출물 | 확인 방법 |
|---|---|
| 엔티티 4종과 스키마 | H2 콘솔에서 4개 테이블과 제약 조건을 확인한다 |
| 공통 상수 | 유형·상태·중요도·역할·작성자 구분 enum이 백엔드와 프론트엔드에서 동일한 값을 가진다 |
| API 명세와 **스텁 응답** | 9장 엔드포인트 12개가 Swagger에 노출되고, 목 데이터로 200을 반환한다 |
| **보안 경로 패턴** | `/api/feedbacks/**` 공개, `/api/admin/**` 인증으로 선언되어 이후 `SecurityConfig`를 수정할 일이 없다 |
| 데모 로그인 장치 | `dev` 프로필에서 계정 4종 전환이 되고, 운영 프로필에서는 404를 반환한다 |
| 시드 데이터 | 프로젝트 5건과 피드백 약 40건이 들어가고 상태·유형·중요도가 고르게 분포한다 |
| **프론트엔드 라우트 전체 선언** | 사용자용과 관리용의 모든 경로가 빈 화면으로 열린다 |
| **라이브러리 일괄 설치** | 드래그, 차트, 아이콘 라이브러리가 설치되어 이후 의존성 파일을 열 일이 없다 |
| 로컬 실행 확인 | 전원이 백엔드와 프론트엔드를 동시에 기동하고 `/api` 프록시 호출에 성공한다 |

스텁 응답과 라우트 선언이 이 단계의 핵심이다.
이 둘이 있어야 C와 D가 백엔드를 기다리지 않고 화면을 만들 수 있다.

#### 0-2단계 · 디자인 기반 (D)

D가 스타일 규칙과 공용 컴포넌트를 먼저 만든다. 그동안 A·B·C는 0-1단계 생성 결과를 읽는다.

| 산출물 | 확인 방법 |
|---|---|
| 색상과 타이포그래피 규칙 | 값이 한 곳에 정의되고 화면에서 직접 색상을 쓰지 않는다 |
| 상태 배지 4종, 중요도 칩 3종 | 공용 컴포넌트로 만들어지고 스텁 데이터로 렌더링된다 |
| 화면 시안 | 사용자용 4종과 관리용 2종의 배치가 정해진다 |

**확인 회의를 한 번 연다.** 각자 자기 담당 영역의 생성 결과를 설명할 수 있어야 1단계를 시작한다.
C와 D의 화면 작업은 0-2단계가 끝난 뒤 시작한다. A와 B는 0-1단계만 끝나면 시작할 수 있다.

#### 1단계 · 기본 기능 (동시)

| 담당 | 작업 | 완료 조건 |
|---|---|---|
| A | 피드백 등록 API | 비회원과 회원 모두 등록에 성공하고 검증 오류가 공통 형식으로 반환된다 |
| B | 관리용 목록 조회 API, 필터와 정렬, 역할별 권한 검사 | 정렬 규칙대로 동작하고 `VIEWER`의 수정 호출이 403을 받는다 |
| C | 관리용 레이아웃, 상단 탭, 칸반 보드 골격 | **스텁 응답으로** 3열 보드와 반영 불가 영역이 표시된다 |
| D | 로그인 화면, 비회원 경고 팝업 | 경고 팝업의 두 버튼이 각각 구글 로그인과 작성 화면으로 이동한다 |

C와 D는 0-2단계의 공용 컴포넌트를 사용한다. 화면에서 색상과 여백을 직접 지정하지 않는다.

#### 2단계 · 1차 통합

| 작업 | 담당 | 완료 조건 |
|---|---|---|
| 관리용 화면의 스텁을 실제 API로 교체 | B·C | 칸반에 실제 데이터가 표시되고 필터와 정렬이 동작한다 |
| 공용 컴포넌트 적용 확인 | C·D | 관리용 화면이 D의 스타일 규칙을 그대로 사용한다. 임시로 만든 요소를 D가 공용으로 흡수한다 |

#### 3단계 · 조회와 처리 (동시)

| 담당 | 작업 | 완료 조건 |
|---|---|---|
| A | 답변 등록·수정 API, 내 문의 조회 API | 데모 계정 `user@demo.local`로 본인 피드백만 조회된다 |
| B | 상태·유형·중요도 변경 API, 대시보드 집계 API | 6개 지표가 시드 데이터 기준으로 정확히 계산된다 |
| C | 답변 탭, 카드 상세 패널 | 비회원 항목이 비활성으로 표시되고 답변 버튼이 없다 |
| D | 작성 화면, 홈 화면 | 링크 진입 시 사이트가 고정되고 홈 진입 시 드롭다운이 나타난다 |

#### 4단계 · 2차 통합

| 작업 | 담당 | 완료 조건 |
|---|---|---|
| 사용자용 등록 흐름 연결 | A·D | 비회원이 링크로 진입해 등록하고 접수 팝업까지 확인한다 |
| 상태 변경 흐름 연결 | B·C | 카드를 다른 열로 이동하면 서버 상태가 바뀌고 새로고침 후에도 유지된다 |

#### 5단계 · 화면 마감 (동시)

| 담당 | 작업 | 완료 조건 |
|---|---|---|
| A | 우선 처리 요청 API | 요청 시 중요도가 상향되고 목록 최상단에 고정된다 |
| B | 대시보드 집계 쿼리 정리 | 피드백 1,000건 기준 대시보드 응답이 지연 없이 반환된다 |
| C | 하단 회전 디스크, 대시보드 차트 | 드래그로 프로젝트가 전환되고 6-1의 화면 구조대로 동작한다 |
| D | 문의 상세 화면, 오류와 빈 목록 안내 | 답변 유무와 네트워크 오류에서 각각 안내 문구가 표시된다 |

로고 이미지는 이 단계 전에 준비한다.

#### 6단계 · 알림과 계정 관리

| C | 관리용 화면 마감, 답변 흐름 연결 확인 | 개발자 계정으로 등록한 답변이 사용자 계정의 문의 상세에 표시된다 |
| D | 계정 관리 화면 | 대기 계정에 역할을 지정해 승인하면 해당 계정으로 접근할 수 있다 |
