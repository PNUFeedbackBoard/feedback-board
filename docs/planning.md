# 통합 피드백 게시판 기획안

부산대학교 AI융합교육원이 운영하는 5개 시스템의 피드백을 한 곳에서 수집하고 처리하는 서비스의 설계 문서다.

- 문서 버전: v1.1
- 최종 수정: 2026-09-15
- 관련 문서: [README](../README.md), [개발환경 설정 가이드](setup-guide.md)

---

## 1. 개요

### 1-1. 목적

현재 5개 시스템은 각각 별도의 경로로 피드백을 받고 있어 전체 접수 현황과 처리 결과를 확인할 수 없다.
이 서비스는 수집 창구를 하나로 모으고, 이용 목적이 다른 세 집단에 각각 필요한 화면을 제공한다.

| 이용자 | 현재 문제 | 제공하는 기능 |
|---|---|---|
| 실사용자 | 신고 창구가 시스템마다 다르고 처리 여부를 알 수 없다 | 시스템별 링크를 통한 피드백 등록, 답변과 진행 상태 조회 |
| 개발자 | 피드백이 여러 경로로 분산되어 누락된다 | 프로젝트별 칸반 보드와 답변 대기열 |
| 교육원 운영진 | 5개 프로젝트의 전체 현황을 한 번에 볼 수 없다 | 전체 현황 대시보드 |

개발자는 프로젝트 단위로 나누어 보아야 하고, 운영진은 전체를 합쳐 보아야 한다.
두 요구를 한 화면에서 만족시킬 수 없으므로 **화면을 목적별로 분리한다.**
홈은 전체 현황 대시보드, 프로젝트 상세는 해당 프로젝트의 작업 화면으로 둔다.

### 1-2. 대상 사이트

| 코드 | 이름 |
|---|---|
| `codeplace` | 코드플레이스 |
| `aipms` | AIPMS |
| `aicms` | AICMS |
| `aicap` | AI역량지원시스템 |
| `srvadm` | pickle (서버관리) |

프로젝트 목록은 DB에서 관리하며 추가할 수 있다. 각 프로젝트는 화면 이동 메뉴에 사용할 로고 이미지를 가진다.

## 2. 시스템 구성

React 애플리케이션 하나를 경로로 분리하고, 스프링부트 서버 하나를 공유한다.

```
   실사용자  ──▶  /  ·  /write  ·  /my      사용자용 화면
                                              │
   개발자    ──▶  /admin/**                   │  /api/**
   열람자    ──▶  (인증 + 권한 검사)          │
                                              ▼
                              Spring Boot 3.5.6 / JDK 21 / JPA
                                              │
                                        PostgreSQL
```

- 프론트엔드: React (Vite) 단일 프로젝트. 라우팅으로 사용자용과 관리용을 구분한다.
- 백엔드: Spring Boot 3.5.6 / JDK 21 / JPA / Spring Security. 로컬 개발은 H2, 운영은 PostgreSQL을 사용한다.
- 권한 검사는 화면이 아니라 API에서 수행한다. 관리용 주소를 직접 입력해도 데이터를 얻을 수 없다.

## 3. 사용자와 권한

### 3-1. 역할

역할은 네 가지이며, 관리용 사이트에 접근할 수 있는 역할은 `DEVELOPER`와 `VIEWER` 두 가지다.

| 역할 | 코드 | 권한 |
|---|---|---|
| 개발자 | `DEVELOPER` | 전체 프로젝트 조회 및 수정, 상태 변경, 답변 작성, 유형·중요도 변경, 계정 승인과 역할 부여 |
| 열람자 | `VIEWER` | 전체 프로젝트 조회, 대시보드 조회, 우선 처리 요청 |
| 일반 사용자 | `USER` | 피드백 등록, 자신이 등록한 피드백과 답변 조회 |
| 비회원 | 없음 | 피드백 등록 |

- 모든 개발자는 동일한 권한을 가진다. 담당 프로젝트를 구분하지 않으므로 부재 시 다른 개발자가 대신 처리할 수 있다.
- 계정 승인 권한 또한 모든 개발자가 가진다. 승인 절차를 한 사람에게 의존하지 않기 위한 결정이다.
- 열람자는 상태 변경과 답변 작성을 할 수 없다. 처리 진행 상황이 의도치 않게 바뀌는 것을 방지한다.

### 3-2. 계정 승인

관리용 사이트는 승인된 계정만 사용할 수 있다.

| 순서 | 처리 내용 | 계정 상태 |
|---|---|---|
| 1 | 구글 로그인으로 `/admin`에 최초 접근하면 계정 레코드를 생성한다 | `PENDING` |
| 2 | 승인 대기 안내 화면을 표시하고 모든 기능을 차단한다 | `PENDING` |
| 3 | 기존 개발자가 역할을 지정하고 승인한다 | `ACTIVE` |
| 4 | 부여된 역할의 권한으로 이용한다 | `ACTIVE` |

최초 개발자 계정 한 건은 DB에 직접 등록해 초기화한다. 이후의 계정은 화면에서 승인한다.

## 4. 피드백 규칙

### 4-1. 유형

| 유형 | 코드 | 정의 |
|---|---|---|
| 오류 신고 | `BUG` | 서비스 이용 중 발생한 오류 또는 비정상 동작 |
| 기능 제안 | `FEATURE` | 추가를 요청하는 기능 |
| 기타 의견 | `ETC` | 위 두 유형에 해당하지 않는 의견 |

유형은 작성자가 선택하고, 개발자가 변경할 수 있다.
작성자가 유형을 잘못 선택한 경우 분류를 바로잡기 위한 기능이다.

### 4-2. 진행 상태

상태는 네 가지이며, 칸반 보드는 이 중 세 가지를 열로 사용한다.

| 상태 | 코드 | 전환 시점 | 전환 주체 | 칸반 위치 |
|---|---|---|---|---|
| 접수 | `RECEIVED` | 피드백이 등록된 직후 부여되는 초기 상태 | 시스템 | 1열 (진행 전) |
| 처리 중 | `IN_PROGRESS` | 내용을 확인하고 수정 작업에 착수한 시점 | 개발자 | 2열 (진행 중) |
| 처리 완료 | `DONE` | 수정이 반영되어 추가 조치가 필요 없는 시점 | 개발자 | 3열 (완료) |
| 반영 불가 | `REJECTED` | 중복·오신고이거나 현재 반영이 어렵다고 판단한 시점 | 개발자 | 보드 밖 (별도 목록) |

`REJECTED`는 칸반 열을 차지하지 않는다. 보드 하단의 "반영 불가 N건" 영역에서 펼쳐 조회한다.
보드에는 처리해야 할 항목만 남기기 위한 구성이다.

상태 배지 색상은 접수 파랑, 처리 중 주황, 처리 완료 초록, 반영 불가 회색을 사용한다.

### 4-3. 중요도

중요도 값은 `HIGH`, `NORMAL`, `LOW` 세 가지이며 기본값은 `NORMAL`이다.
서로 다른 두 필드로 관리한다.

| 필드 | 입력 주체 | 용도 |
|---|---|---|
| `reported_priority` | 작성자가 등록 시 선택 | 작성자가 체감한 긴급도. 참고용이며 정렬에 사용하지 않는다 |
| `priority` | 개발자가 확정 | 정렬 기준값. 등록 시점에는 `reported_priority`와 같은 값으로 시작한다 |

작성자가 선택한 값을 그대로 정렬에 사용하면 대부분의 피드백이 `HIGH`로 등록되어 정렬이 무의미해진다.
따라서 작성자의 입력은 보존하되, 정렬은 개발자가 확정한 값으로만 수행한다.
상세 화면에는 두 값을 함께 표시한다.

### 4-4. 우선 처리 요청

열람자가 특정 피드백을 먼저 처리하도록 요청하는 기능이다.

| 항목 | 동작 |
|---|---|
| 버튼 동작 | 토글. 다시 누르면 해제된다. 요청 가능 건수에 제한은 없다 |
| 중요도 | 요청 시 `priority`를 `HIGH`로 변경한다 |
| 알림 | 요청 시 개발자 전원에게 메일을 발송한다 |
| 정렬 | 어떤 정렬 기준을 선택해도 목록 최상단에 고정하고 배지를 표시한다 |
| 해제 | 요청한 열람자 본인만 해제할 수 있다 |

요청 이후 개발자가 `priority`를 다시 낮추는 것은 가능하다. 이 경우에도 배지와 상단 고정은 유지된다.

### 4-5. 정렬과 필터

정렬은 우선 처리 요청 여부를 1순위로 적용한 뒤, 선택한 기준을 2순위로 적용한다.

| 정렬 기준 | 순서 |
|---|---|
| 중요도순 | 우선 처리 요청 → `HIGH` → `NORMAL` → `LOW` → 동일 시 최신순 |
| 최신순 | 우선 처리 요청 → 등록일 내림차순 |
| 오래된순 | 우선 처리 요청 → 등록일 오름차순 |

필터 항목은 사이트, 진행 상태, 유형, 기간, 회원 여부다.

## 5. 사용자용 사이트

### 5-1. 화면 흐름

```
                        로그인 화면
                    ┌────────┴────────┐
              구글 로그인          비회원으로 계속
                    │                  │
                    │            비회원 경고 팝업
                    │            ┌─────┴─────┐
                    │        [로그인]      [계속]
                    │            │            │
                    ▼            │            │
              홈 (내 문의) ◀──────┘            │
                    │                         │
             새 질문 적기                      │
                    │                         │
                    └──────────┬──────────────┘
                               ▼
                        피드백 작성 화면
                               ▼
                    "질문이 접수되었습니다"
```

비회원은 홈을 거치지 않고 작성 화면으로 이동한다.

### 5-2. 사이트 지정

피드백의 대상 사이트는 진입 링크로 결정한다.

- 각 시스템에 `https://{서비스주소}/?site=aipms` 형식의 링크를 배치한다.
- 링크로 진입한 경우 사이트가 자동 지정되며 작성자는 변경할 수 없다. 대상 사이트 오분류를 방지한다.
- 회원이 홈에서 `새 질문 적기`를 선택한 경우에는 사이트 정보가 없으므로, 이 경우에만 사이트 선택 드롭다운을 표시한다.

### 5-3. 화면 명세

#### 로그인 화면 `/`

서비스 설명과 함께 `구글로 로그인`, `비회원으로 계속` 두 개의 버튼을 배치한다.

`비회원으로 계속`을 선택하면 다음 내용의 모달을 표시한다.

- 안내 문구: 비회원은 답변을 받을 수 없으며, 등록한 내용과 진행 상태를 다시 확인할 수 없다.
- `로그인` 버튼: 구글 로그인으로 이동한다.
- `계속` 버튼: 작성 화면으로 이동한다.

#### 홈 `/home` — 회원 전용

- `새 질문 적기` 버튼
- 본인이 등록한 피드백 목록. 최신순으로 정렬하며 사이트, 제목, 유형, 상태 배지, 등록일, 답변 여부를 표시한다.
- 목록이 비어 있는 경우 안내 문구를 표시한다.

#### 피드백 작성 `/write`

| 항목 | 입력 형태 | 필수 | 제약 |
|---|---|---|---|
| 사이트 | 고정 표시 또는 드롭다운 | 필수 | 링크로 진입한 경우 변경 불가 |
| 유형 | 라디오 버튼 3개 | 필수 | 기본 선택값 없음 |
| 긴급도 | 라디오 버튼 3개 | 필수 | 기본값 `NORMAL` |
| 제목 | 단일 행 입력 | 필수 | 최대 100자 |
| 내용 | 여러 행 입력 | 필수 | 10자 이상 2,000자 이하 |

등록에 성공하면 "질문이 접수되었습니다" 팝업을 표시한다.
회원은 홈으로, 비회원은 로그인 화면으로 이동하며 비회원 세션은 종료된다.

#### 문의 상세 `/my/{id}` — 회원 전용

등록한 제목과 내용, 유형, 등록일, 현재 상태 배지, 개발자 답변을 표시한다.
답변이 없는 경우 안내 문구를 표시한다.

작성자는 등록한 피드백을 수정하거나 삭제할 수 없다.
처리 중인 항목이 변경되거나 삭제되면 처리 이력이 어긋나기 때문이다.

## 6. 관리용 사이트

### 6-1. 화면 구조

화면 이동은 두 축으로 구성한다. 하단은 프로젝트를 전환하고, 상단은 선택된 프로젝트 내부의 메뉴를 전환한다.

```
┌─────────────────────────────────────────────────────┐
│  통합 피드백 게시판                    계정 이름 ▾   │  공통 헤더
├─────────────────────────────────────────────────────┤
│ ╭──────────╮ ╭────────╮                             │  상단 탭
│ │ 개발 보드 │ │  답변  │                             │  (프로젝트 내 메뉴)
├─┴──────────┴─┴────────┴─────────────────────────────┤
│                                                     │
│              칸반 보드 또는 답변 목록                 │
│                                                     │
├─────────────────────────────────────────────────────┤
│                   ⬤ 선택된 프로젝트                  │  하단 디스크
│              ○                      ○               │  (프로젝트 전환)
│         ╲______화면 아래로 잘림______╱               │
└─────────────────────────────────────────────────────┘
```

- **하단 디스크**: 원형 메뉴의 위쪽 일부만 화면에 노출한다. 프로젝트 로고를 호를 따라 배치하고, 좌우 드래그 또는 로고 클릭으로 회전한다. 최상단에 위치한 프로젝트가 선택된다. 슬롯 하나는 홈(전체 현황 대시보드) 진입점으로 사용한다.
- **상단 탭**: 브라우저 탭 형태로 `개발 보드`와 `답변` 두 개를 배치한다.

### 6-2. 홈 — 전체 현황 대시보드

조회 전용 화면이다. 이 화면에서는 상태 변경이나 답변 작성을 수행하지 않는다.
상단에 상태별 건수 카드를 배치하고, 그 아래에 차트 네 개, 하단에 우선 처리 요청 목록과 최근 접수 10건을 배치한다.

| 지표 | 산출 방식 |
|---|---|
| 상태별 건수 | 상태별 건수 합계 |
| 프로젝트별 현황 | 프로젝트와 상태의 교차 집계. 누적 막대 |
| 유형별 비율 | 유형별 건수를 전체 건수로 나눈 값. 도넛 |
| 기간별 추이 | 일자별 접수 건수. 기본 조회 범위 30일. 선 그래프 |
| 평균 처리 소요 시간 | `closed_at - created_at`의 평균. `DONE`과 `REJECTED`만 집계 |
| 이용자 수 | 피드백을 1건 이상 등록한 고유 사용자 수. 비회원은 별도 집계 |

### 6-3. 개발 보드 탭

진행 전, 진행 중, 완료 세 개 열로 구성한 칸반 보드다.

- 카드 표시 항목: 우선 처리 요청 배지, 중요도, 제목, 유형, 경과일, 회원 여부, 답변 여부
- 카드를 다른 열로 이동하면 상태가 변경된다. 카드 선택 시 열리는 상세 패널에서도 변경할 수 있다.
- 상세 패널에서 전체 내용 확인, 유형 변경, 중요도 변경, 답변 화면 이동을 제공한다.
- 상단에 정렬, 유형, 기간 필터를 배치한다. 정렬은 각 열 내부에 적용한다.
- 보드 하단에 반영 불가 항목을 접은 상태로 배치한다.

### 6-4. 답변 탭

답변을 작성하는 목록형 화면이다. 기본 필터는 `답변 필요`, 기본 정렬은 오래된순이다.

- 항목 표시: 우선 처리 요청 배지, 중요도, 제목, 유형, 등록일, 작성자 회원 여부, 현재 상태, 내용 일부
- 비회원이 등록한 피드백은 답변 대상이 아니다. 비회원 표시와 함께 비활성 상태로 노출하며 답변 버튼을 제공하지 않는다.
- 답변은 피드백 1건당 1건만 등록할 수 있으며, 등록 후 수정할 수 있다.
- 답변 등록 시 상태를 `DONE`으로 함께 변경하는 선택 항목을 제공한다.

### 6-5. 계정 관리 — 개발자 전용

헤더의 계정 메뉴에서 진입한다.
승인 대기 목록에서 이메일, 이름, 가입일을 확인하고 역할을 지정해 승인하거나 거절한다.
기존 계정의 역할 변경과 비활성화도 이 화면에서 처리한다.

## 7. 알림

| 발생 시점 | 수신자 | 수단 |
|---|---|---|
| 개발자가 답변을 등록한 때 | 해당 피드백 작성자 (회원) | 이메일, 사이트 내 표시 |
| 열람자가 우선 처리를 요청한 때 | 개발자 전원 | 이메일 |

- 비회원은 이메일을 수집하지 않으므로 알림을 발송하지 않는다.
- 답변을 수정한 경우에는 발송하지 않는다. 사소한 수정마다 메일이 발송되는 것을 방지한다.
- 발송 실패는 기록만 남기고 요청 자체는 성공 처리한다. 알림 실패가 피드백 처리를 막지 않도록 한다.
- 메일 본문에는 제목과 조회 링크만 포함하고 내용 전문은 포함하지 않는다.

## 8. 데이터 모델

| 테이블 | 주요 컬럼 | 비고 |
|---|---|---|
| `projects` | `code`, `name`, `logo_url`, `site_url`, `sort_order` | `sort_order`는 하단 디스크의 배치 순서 |
| `users` | `email`, `name`, `google_sub`, `role`, `status` | `role`: `USER`, `DEVELOPER`, `VIEWER` / `status`: `PENDING`, `ACTIVE`, `DISABLED` |
| `feedbacks` | `project_id`, `author_id`, `author_type`, `title`, `content`, `category`, `status`, `reported_priority`, `priority`, `priority_requested`, `created_at`, `first_answered_at`, `closed_at` | 비회원은 `author_id`가 `NULL`, `author_type`이 `GUEST` |
| `answers` | `feedback_id`, `author_id`, `content`, `created_at`, `updated_at` | 피드백 1건당 1건 |

- `first_answered_at`과 `closed_at`은 대시보드의 평균 처리 소요 시간 산출에 사용한다.
- `priority_requested`는 우선 처리 요청 여부를 나타내며 정렬의 1순위 기준이다.
- 비회원이 등록한 피드백도 저장한다. 통계 집계와 중복 신고 확인에 필요하다.

## 9. API 초안

| 메서드 | 경로 | 접근 권한 | 설명 |
|---|---|---|---|
| `GET` | `/api/projects` | 공개 | 프로젝트 목록 |
| `POST` | `/api/feedbacks` | 공개 | 피드백 등록. 비회원 허용 |
| `GET` | `/api/me/feedbacks` | `USER` | 본인이 등록한 피드백 목록 |
| `GET` | `/api/me/feedbacks/{id}` | `USER` | 본인 피드백 상세. 답변 포함 |
| `GET` | `/api/admin/dashboard` | `DEVELOPER`, `VIEWER` | 전체 현황 지표 |
| `GET` | `/api/admin/feedbacks` | `DEVELOPER`, `VIEWER` | 목록 조회. `project`, `status`, `category`, `sort`, `from`, `to` |
| `GET` | `/api/admin/feedbacks/{id}` | `DEVELOPER`, `VIEWER` | 상세 조회 |
| `PATCH` | `/api/admin/feedbacks/{id}` | `DEVELOPER` | 상태, 유형, 중요도 변경 |
| `PUT` | `/api/admin/feedbacks/{id}/answer` | `DEVELOPER` | 답변 등록 및 수정 |
| `POST` | `/api/admin/feedbacks/{id}/priority-request` | `VIEWER` | 우선 처리 요청 토글 |
| `GET` | `/api/admin/users` | `DEVELOPER` | 계정 목록 |
| `PATCH` | `/api/admin/users/{id}` | `DEVELOPER` | 계정 승인 및 역할 변경 |

`VIEWER` 역할이 `PATCH /api/admin/feedbacks/{id}`를 호출하면 403을 반환한다.

## 10. 인증

- 사용자용과 관리용 모두 구글 로그인만 사용한다. 자체 비밀번호는 발급하지 않는다.
- 관리용 사이트는 계정 상태가 `ACTIVE`이고 역할이 `DEVELOPER` 또는 `VIEWER`인 경우에만 접근을 허용한다.
- 비회원은 계정을 생성하지 않는다. 세션 종료 후 등록 내역을 조회할 수 없다.

## 13. 개발 순서

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| 1 | 엔티티 4종과 스키마 정의, 프로젝트 5건 시드 데이터 | 애플리케이션이 기동되고 프로젝트 조회 API가 5건을 반환한다 |
| 2 | 피드백 등록 API, 작성 화면, 링크 기반 사이트 지정 | 비회원이 링크로 진입해 피드백을 등록하고 접수 팝업을 확인한다 |
| 3 | 구글 로그인, 홈 화면, 문의 상세 | 회원이 로그인해 본인이 등록한 피드백과 상태를 조회한다 |
| 4 | 관리용 목록 API, 역할 기반 권한 검사, 칸반 보드 | 개발자가 카드를 이동해 상태를 변경하고, 열람자 계정은 403을 받는다 |
| 5 | 답변 등록 및 수정 API, 답변 탭 | 개발자가 등록한 답변을 회원이 문의 상세에서 확인한다 |
| 6 | 대시보드 집계 API, 홈 화면 차트 | 6개 지표가 실제 데이터로 표시된다 |
| 7 | 하단 디스크, 상단 탭, 상태 배지 등 화면 마감 | 6-1에 정의한 화면 구조대로 동작한다 |
| 8 | 우선 처리 요청, 이메일 알림, 계정 관리 화면 | 열람자의 요청이 개발자에게 메일로 도달한다 |
| 9 | 배포, 5개 시스템에 진입 링크 배치 | 실사용자가 각 시스템에서 피드백을 등록한다 |

1~3단계는 순차로 진행한다. 4~5단계와 6단계는 프론트엔드와 백엔드를 나누어 병렬로 진행할 수 있다.
