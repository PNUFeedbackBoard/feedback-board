# 0-2단계 · 디자인 기반

담당: **D**
선행 조건: 0-1단계(공통 기반) 생성 완료
다음 단계: 1단계 — C와 D가 화면 작업을 시작한다

---

## 왜 이 단계가 따로 있나

C는 관리용 화면을, D는 사용자용 화면을 만든다.
두 사람이 각자 색과 여백을 정하면 **같은 서비스로 보이지 않고**, 나중에 한쪽을 통째로 다시 만들어야 한다.

그래서 D가 먼저 규칙과 공용 컴포넌트를 만들고, **C가 그 위에서 시작한다.**
그동안 A·B·C는 0-1단계 생성 결과를 읽는다.

이 단계가 끝나야 C와 D의 화면 작업이 시작된다. A와 B는 0-1만 끝나면 시작할 수 있다.

---

## 산출물 3가지

### 1. 색상과 타이포그래피 규칙

파일: `frontend/src/styles/tokens.css`

**모든 값을 CSS 변수로 한 곳에 정의한다.** 화면에서는 이 변수만 쓰고 `#hex` 를 직접 쓰지 않는다.

정의할 것:

```
표면       배경, 카드 표면, 한 단계 들어간 표면, 테두리
글자       기본, 흐린 글자, 더 흐린 글자
상태       접수 / 처리 중 / 처리 완료 / 반영 불가  (각각 글자색 + 배경색 한 쌍)
강조       우선 처리 요청과 중요도 '높음'에 쓰는 색 1개
글자 크기   3~4단계면 충분하다 (제목 / 본문 / 작은 글씨 / 아주 작은 라벨)
글자 굵기   2~3단계
간격       4px 배수로 5~6단계 (4, 8, 12, 16, 24, 32)
모서리     1~2종류
그림자     1~2종류. 남발하면 화면이 납작해진다
```

**이미 기획서에서 정해진 제약** (바꾸려면 팀에 먼저 말한다):

| 상태 | 색 계열 |
|---|---|
| 접수 | 파랑 |
| 처리 중 | 주황 |
| 처리 완료 | 초록 |
| 반영 불가 | 회색 |

### 2. 공용 컴포넌트

폴더: `frontend/src/components/common/`

C가 관리용 화면에서 **그대로 가져다 쓴다.** 아래 props 이름은 계약이므로 바꾸지 않는다.

| 컴포넌트 | 사용법 | 표현할 것 |
|---|---|---|
| `StatusBadge` | `<StatusBadge status="RECEIVED" />` | 상태 4종. 색만으로 구분하지 말고 글자를 함께 둔다 |
| `PriorityChip` | `<PriorityChip priority="HIGH" />` | 중요도 3종. 높음만 눈에 띄고 보통·낮음은 조용해야 한다 |
| `CategoryTag` | `<CategoryTag category="BUG" />` | 유형 3종 |
| `PriorityRequestBadge` | `<PriorityRequestBadge />` | 우선 처리 요청 표시. 목록 최상단 고정 항목에 붙는다 |

받는 값은 **영문 코드**(`RECEIVED`, `HIGH`, `BUG`)다.
한국어 표기는 컴포넌트 안에서 `src/constants/enums.js` 를 보고 변환한다.
화면에서 한국어 문자열을 직접 넘기지 않는다.

확인 방법: 0-1단계의 스텁 데이터로 관리용 목록을 열었을 때 배지와 칩이 모두 렌더링되어야 한다.

### 3. 화면 시안

폴더: `docs/design/`

6종을 만든다. 도구는 자유이고(피그마, 그림 파일 무엇이든) 폴더에 이미지나 링크를 둔다.

| 시안 | 화면 | 참고 |
|---|---|---|
| 1 | 로그인 | 버튼 2개, 비회원 경고 팝업 포함 |
| 2 | 피드백 작성 | 사이트 고정 표시와 드롭다운 두 경우 |
| 3 | 홈 (내 문의 목록) | 목록이 비었을 때도 함께 |
| 4 | 문의 상세 | 답변 있음 / 없음 두 경우 |
| 5 | 개발 보드 (칸반) | 3열 + 반영 불가 접힌 영역. planning.md 6-3 참고 |
| 6 | 답변 탭 | 비회원 항목 비활성 표시 포함. planning.md 6-4 참고 |

관리용 화면의 구조(상단 탭, 하단 원형 디스크)는 [planning.md 6-1](planning.md) 에 정의돼 있다.
**구조를 바꾸지 말고 그 안을 채운다.** 바꾸고 싶으면 팀에 먼저 말한다.

대시보드 시안은 5단계에 필요하므로 지금 만들지 않아도 된다.

## 먼저 정해야 할 결정

시작하기 전에 답을 정해두면 중간에 막히지 않는다.

- [ ] 상태 배지 모양 — 점 + 글자 / 테두리만 / 배경 채움 중 무엇인가
- [ ] 중요도를 색으로 구분할 것인가, 글자로만 할 것인가
  (상태가 이미 4색을 쓰고 있다. 중요도까지 색을 쓰면 화면이 혼잡해진다)
- [ ] 우선 처리 요청 표시 — 별표인가, 색 테두리인가, 왼쪽 띠인가
- [ ] 다크 모드를 지원할 것인가
  (지원하면 토큰을 두 벌 만들어야 한다. 안 할 거면 지금 명시적으로 빼는 편이 낫다)
- [ ] 본문 서체 — 시스템 기본 / 웹폰트. 웹폰트면 어떤 것인가
- [ ] 목록의 숫자와 날짜 정렬 방식

## 하지 말 것

- **페이지를 구현하지 않는다.** 사용자용 화면 4종은 1·3·5단계에 나눠 만든다
- **관리용 화면을 만들지 않는다.** C의 영역이다
- **토큰에 없는 색을 컴포넌트 안에서 쓰지 않는다.** 필요하면 토큰에 먼저 추가한다
- **`src/pages/` 를 건드리지 않는다.** 이 단계의 작업은 `styles/`, `components/common/`, `docs/design/` 안에서 끝난다

---

## C에게 넘기는 방법

D가 이 세 가지를 끝내면 C가 그 위에서 관리용 화면을 시작한다.

1. `tokens.css` 와 `components/common/` 을 `develop` 에 먼저 올린다
2. 팀에 한 줄로 알린다 — "토큰과 배지 올렸습니다. 이제 화면 작업 시작하셔도 됩니다"
3. C가 쓰다가 없는 것이 필요하면 D에게 요청한다.
   **대기가 길어지면 C가 자기 화면에 임시로 만들고, 2단계 통합에서 D가 공용으로 흡수한다.**
   기다리느라 멈추지 않는다
